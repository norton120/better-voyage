# 08 — Natural-language summary

**Status:** draft

Every surfaced candidate gets a **1–3 sentence** plain-English recap —
"what is this passage going to feel like?" — so the skipper can compare
options at a glance. These recaps are generated by an LLM (Claude
Haiku), not a rule engine: the inputs are rich and interlinked, and a
model produces better prose than a decision tree of templates.

## Constraints

- **Strictly 1–3 sentences.** Not a paragraph. Not a blog post.
- **Second person, present tense.** "You'll get a beam reach..."
- **Concrete numbers** where they matter (peak wind, max seas, ETA,
  tack count).
- **Honest tradeoffs.** If there's a downside, name it.
- **No jargon** a weekend sailor wouldn't know.
- **Prose only.** No markdown, no lists, no emoji, no preamble.

## Model

- **Claude Haiku 4.5** (`claude-haiku-4-5`). Fast, cheap, excels at
  structured-to-prose. ~500 tokens in / ~150 tokens out per candidate;
  5–10 candidates per voyage.
- Anthropic Python SDK.
- Temperature `0.3` — tight variation while allowing natural phrasing.
- `max_tokens = 150` (roughly 3 sentences).
- One call per surfaced candidate. Batching multiple candidates into
  one call is cheaper but makes attribution harder on failures; stick
  with one per candidate.

## Input shape (digest)

We don't hand the LLM the raw candidate. A `digest_candidate()` helper
turns the scored route into a compact, pre-analyzed JSON payload —
model focuses on composing, we keep the analysis testable.

```json
{
  "voyage": {
    "origin_name":      "Annapolis",
    "destination_name": "Norfolk",
    "objective":        "fastest"
  },
  "candidate": {
    "rank":            1,
    "depart_at_local": "Mon 2026-04-21 06:00 EDT",
    "arrive_at_local": "Tue 2026-04-22 04:30 EDT",
    "duration_h":      22.5,
    "score":           82,
    "night_crossing":  true,
    "wind_character":  "steady 12–15 kt beam reach most of day 1",
    "seas_character":  "calm day 1, building to 2.1 m Tue afternoon",
    "current_character": "favorable 14 of 22 hours",
    "tack_count":      4
  },
  "contingencies": [
    { "kind": "tap_out_marina",    "target": "Deltaville", "leg_h": 8 },
    { "kind": "escape_hatch_route", "trigger": "seas > 2.0 m" }
  ]
}
```

Times in the user's local tz (from `VoyageRequest.window.tz`) so the
model doesn't convert. Characterizations are pre-computed strings, not
raw arrays — the model doesn't need to crunch forecast data.

`digest_candidate()` lives in `app/services/summary.py`, is pure, and
has golden tests of its own (input candidate → expected digest JSON).

## System prompt

Stable per deployment. Kept at
`app/data/prompts/summary_system.md`; loaded at startup and hashed
into the cache key.

Shape:

```
You are a concise sailing assistant. Given structured JSON about a
candidate passage, produce a 1–3 sentence recap for the skipper.

Rules:
- Second-person present tense. "You'll..." not "One would..."
- Lead with the passage's character or the most actionable fact.
- Mention one concrete number when it materially shapes the day
  (peak wind, max seas, ETA, tack count).
- If there's a meaningful tradeoff, name it. Don't soften.
- No jargon a weekend sailor wouldn't know.
- No preamble, no markdown, no lists, no emoji.
- Length: strictly 1–3 sentences.

<3–4 few-shot examples follow: input JSON → output prose>

Respond with ONLY the recap text.
```

Few-shot examples cover: fast beam-reach passage, uncomfortable
close-hauled slog with a good tap-out, multi-day passage with a night
crossing, short tide-gated leg.

Once the prompt (system + few-shot) exceeds the Haiku cache threshold,
mark it with `cache_control: {type: "ephemeral"}` for cost savings on
repeat submissions.

## Fallback

If the Anthropic call fails (no API key, network error, rate limit,
timeout): **do not fail the voyage job.** A working route is useful
without a recap.

- Log `summary.llm_fallback` with the reason.
- Emit a templated recap:
  `"Depart {depart_at_local}, arrive {arrive_at_local}
  ({duration_h:.0f} h). Score {score:.0f}/100."`
- Set `bv:summarySource = "fallback"` on the route's extensions so a
  UI can render it less prominently.
- Force-fallback via `BV_SUMMARY_MODE=fallback_only` for offline
  deployments or tests.

## Caching

LLM calls are not free; repeat voyages would pay twice.

- Cache key: `sha256(digest_json + system_prompt_version + model_id)`.
- Cache table lives in SQLite next to other caches (doc 11).
- TTL matches the forecast TTL (`forecast_cache_ttl_s`); a different
  forecast means different env numbers means a different digest
  anyway, but we want the cache to drop when the underlying data
  churns.

Cache hits populate `summaryMd` without an API call;
`bv:summarySource = "cache"`.

## Determinism

LLMs are not bit-deterministic. We accept that.

- Tests use **contract assertions**, not exact-string matches:
  - Length: 1–3 sentences (regex).
  - Mentions the local departure day or time.
  - Contains at least one concrete forecast number when the digest
    contained one.
  - No forbidden tokens (markdown headers, bullet points, emoji,
    meta-commentary).
- Temperature 0.3 + stable system prompt keeps practical variation
  low. Two runs of the same digest should feel like minor edits, not
  different copy.

## Dependencies (land at M6)

- `anthropic>=0.45` — official SDK.

## Observability

- Span `summary.render` per candidate, attributes:
  - `bv.summary.model`
  - `bv.summary.source` ∈ `llm` / `cache` / `fallback`
  - `bv.summary.cache_outcome` ∈ `hit` / `miss` / `bypassed`
  - `bv.summary.tokens_in`, `bv.summary.tokens_out` (LLM path only)
  - `bv.summary.wallclock_seconds`
- Log `summary.done` at DEBUG with the generated text (keeps
  production logs from becoming a review corpus).
- Metrics:
  - `bv.summary.requests{source}` counter
  - `bv.summary.duration_seconds{source}` histogram
  - `bv.summary.tokens{direction=in|out}` counter
  - `bv.summary.failures{reason}` counter

## Testing

- **Unit:** `digest_candidate()` — golden tests (input → expected
  digest).
- **Unit:** fallback templater — exact string match.
- **Contract tests** against recorded LLM responses
  (`pytest-anthropic` or manual response fixtures). Assertions are
  on shape/content (length, mentions), not exact text.
- **Offline default:** `conftest.py` sets
  `BV_SUMMARY_MODE=fallback_only` so the suite never needs an API key.
  A small live-integration subset runs in CI under
  `BV_SUMMARY_MODE=llm` with a real key, gated from the default
  matrix.

## Open questions

- **Multi-candidate batching** — one LLM call producing all 5 recaps
  is cheaper and lets the model contrast options. Attribution on
  partial failures is harder. Post-MVP.
- **Localization** — English only for MVP. System prompt is a string,
  so swapping per locale is mechanical when we want it.
- **"Why?" expansion** — on-demand second call that explains one
  score component in detail. Post-MVP; backed by the PlanTrace.
- **User corrections** — let a user accept/reject/edit a summary and
  feed that back into the prompt as a few-shot example. Post-MVP.
